The first version: a `check-installs` command that fails a build wherever npm could run a package's install scripts, holding a repository to npm's own `ignore-scripts` setting rather than reading the commands it runs.

- **Rules.** Every package root, the repository's root and any folder with a `package.json` of its own that no package above it lists as a workspace, holds a `.npmrc` that sets `ignore-scripts=true`, with workspace globs read as npm reads them, brace lists expanded and `!` entries leaving folders out. No `.npmrc` sets it to anything else, each read as npm's ini reader reads it. Every Dockerfile stage that runs npm or npx sets `npm_config_ignore_scripts=true` with ENV or ARG before it, a `FROM` an image starting a stage with the setting unset and a `FROM` an earlier stage inheriting its setting, and no RUN turns install scripts back on for its own npm.
- **Command.** `check-installs` reads every `package.json`, `.npmrc` and Dockerfile git tracks or would add, names each file that breaks a rule, with its line where there is one, and exits 0 on a pass, 1 on a refusal and 2 with how to run it when given an argument or run outside a git repository.
- **Function.** `installProblems`, `packageRootsOf`, `npmrcProblems`, `dockerfileProblems`, `isDockerfile` and `repositoryRoot` are exported with their types.
- **Docs.** The README says what the rule is and why, how hooks are set up under it with `npm run prepare`, what the check reads, and what a failure looks like.
- **Tests.** A package root without a `.npmrc`, a setting left out or turned back on, a nested package root that is no workspace, a workspace that needs no `.npmrc`, a multi-stage Dockerfile, a setting made after its RUN and a continued RUN are each checked, through the command in throwaway repositories and through the rules alone.
